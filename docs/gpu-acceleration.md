# 拟合提速方案（GPU 加速）

写于 2026-11-06，供新会话接手。当前拟合引擎是 `tools/fit` 的 fit4（说明见 `tools/fit/README.md`）。

## 现状

- **全片批量**：22 个拟合单元，约 30 小时。单人镜头 20～40 分钟，多实例镜头 2～5 小时。
- **硬件**：RTX 2060 6GB，14GB 内存，12 线程。
- **耗时构成**：全部单元合计约 65.6 小时，统计自 `.data/fit/*/fit.log` 中的"完成：…分项"。

| 阶段 | 占比 | 实际在做什么 | 运行位置 |
|---|---|---|---|
| perframe（逐帧精修） | 31% | 内部又是渲染 + 光流 + 雅可比 + 求解 | 混合 |
| jac（雅可比） | 19% | 用 Cubism Core 做有限差分：约 170 个可见参数，每个参数要做一次 `csmUpdateModel`（10～14ms） | **CPU**（Core 是 asm.js） |
| solve（求解） | 15% | LM 正规方程、带状矩阵 | CPU（Node） |
| render（渲染） | 15% | Chrome 渲染，像素读回 Node | GPU + 读回 |
| flow（光流） | 14% | OpenCV DIS 稠密光流 | **CPU**（当前 opencv-python 不带 CUDA） |
| 其他 | 6% | 外观常量、眼睛开合搜索、打分 | 混合 |

**结论**：GPU 现在只负责画图，真正的瓶颈是 CPU 上的 Core 变形（雅可比）、光流和求解。

## 方案一：在现有引擎上做快速改进（1～3 天，预计提速 4～8 倍）

改动小、风险低，结果仍然和 Core 逐位一致。

1. **稀疏关键帧拟合，而不是逐帧拟合**
   - VTS 本身带平滑（smoothing 4～68），面捕输入的变化是平滑的。所以只在每 4～6 个新画面帧上设节点做轨迹求解，中间帧插值；逐帧精修也只在节点帧上做，再加时间平滑。
   - 求解量降为原来的 1/4～1/6，同时从根上消除闪烁（见 P4 的闪烁问题）。
   - 这是收益最大、改动最小的一项。
2. **在面捕输入空间求雅可比**
   - 改在约 10 维的面捕输入空间求，不再对约 170 个可见参数逐个做有限差分。次级物理（头发、耳朵）用物理脉冲响应近似，现有实现已经有了。
   - Core 调用次数降一个数量级。
   - 精修阶段的头发偏移改成低维参数化：按发束分组，每组 2～3 个自由度。
3. **光流改用 GPU**
   - RTX 2060（Turing）有 NVIDIA 光流硬件 NVOFA。可选：
     - 自己编译带 CUDA 的 OpenCV，用 `cv2.cuda.NvidiaOpticalFlow_2_0`；
     - 在 PyTorch 里跑 RAFT-small，或者 `torchvision.models.optical_flow`。
   - 预计光流阶段提速 10～30 倍。
4. **在 GPU 上算损失和 SSIM，不读回整幅图像**
   - harness 页面里用 shader 计算遮罩内的 SSIM@360 和残差，只读回标量；或者把多帧、多候选画进一张图集，一次性读回。
   - 渲染阶段的读回开销（约占 render 的一半）可以基本消除。
5. **多单元并行**
   - 内存是约束：单个单元峰值约 7GB，所以目前只能一次跑一个。
   - 做完上面 2 和 4 之后，单个单元的内存应能降到 3GB 左右，就可以同时跑 3 个单元。

**预期**：全片从约 30 小时降到 4～8 小时。

## 方案二：可微分的 GPU Live2D 前向模型（1～2 周，预计提速 50～200 倍）

把「参数 → 顶点 → 物理 → 光栅化」整条链路搬到 GPU 上，并做成可微分的。拟合就从有限差分加光流，换成自动求导加梯度下降，所有帧可以批量一起算。

- **变形**：
  - 路线 A：读取 moc3 中的变形器（warp / rotation deformer）、关键形状和关键帧插值规则，用 PyTorch 或 JAX 重新实现。
  - 路线 B：不解析 moc3，用 Core 采样训练一个替代模型（surrogate）：输入参数，输出各 drawable 的顶点，网络可以是按 drawable 分组的小 MLP，或者按关键帧网格做多线性表。它和 Core 存在误差，所以最后仍要用 Core 和 runtime 做一次精修和最终渲染。
- **物理**：Cubism Framework 的物理代码（`CubismPhysics`）是开源的（Live2D Open Software License），可以移植成可微分的 PyTorch 版本，用 Framework 的输出逐帧对拍验证。
- **光栅化**：用 nvdiffrast（或 PyTorch3D）把 drawable 网格按 Core 给出的绘制顺序、贴图、遮罩和混合方式画出来，得到可微分的图像。
- **损失**：直接在 GPU 上算 SSIM@360 加光流或边缘项，对所有帧的输入轨迹一起做梯度下降，时间平滑也作为正则项一起优化。
- **验证**：对随机参数，GPU 前向的顶点和 Core 的输出相比误差 < 0.1px，渲染结果和 runtime 相比 SSIM > 0.99，才算合格。
- **最终产出**仍然导出成参数曲线写进 scene.json，播放器和 runtime 不变。验收用的渲染也仍然走 runtime，保证「拟合用的渲染器和播放器是同一份代码」这条原则：GPU 模型只用来搜参数，最终结果一律由 runtime 渲染并打分。

**风险**：
1. **路线 A 有授权风险**：解析 moc3 二进制可能和 Live2D 的授权条款冲突，动手前需要确认。路线 B 只调用 Core 的公开 API，没有这个问题。
2. **贴图显存**：5 张 4096 贴图在 6GB 显存里够用，但批量不能太大。
3. **混合模式和遮罩**：Cubism 的遮罩（clipping mask）和乘算、屏幕色需要照着实现。

**预期**：全片拟合在 1 小时以内。拟合质量也可能明显提高，因为梯度能直接作用在像素损失上，不再依赖光流的覆盖范围。

## 方案三：换硬件或上云

只要内存不再是约束（例如 32～64GB 的机器），方案一第 5 项的并行度就能直接拉满。云端 GPU（A10、L4 等）配合多实例并行也可以，但 Core 仍然跑在 CPU 上，收益主要来自核数。

## 建议路线

1. 先做方案一的第 1 项（稀疏关键帧加时间平滑）和第 3 项（GPU 光流）。这两项改动最小，同时解决速度和闪烁。
2. 并行做方案二路线 B 的原型：先只做变形替代模型和 nvdiffrast 光栅化，在 s24 上验证能否在分钟级拟合到当前水平。
3. 原型成功，再补可微分物理，替换掉主线。

## 接手须知

- 长任务一律用 `systemd-run --user ... -p MemoryMax=11G` 启动。机器只有 14GB；`/tmp` 是内存盘，当前被 `/tmp/opencode` 占用约 3.6GB。
- 拟合产物在 `.data/fit/`。批量驱动是 `tools/fit/scripts/batch.sh`，支持断点续跑。
- 质检报告：`tools/qa/report.py`；闪烁检测：`tools/fit/scripts/flicker.py`。
- 验收口径以 `docs/pipeline.md` 最后一节为准：普通帧 SSIM@360 ≥ 0.6，目测帧和特效帧以肉眼为准。
